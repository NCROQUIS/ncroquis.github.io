기능별 공용 규격 자세히 보기
랭킹
NcqRank는 대전 없이 점수·클리어 시간 등을 비교할 때 선택해요. 최고·누적·최근 기록과 높은 순·낮은 순을 정하고 같은 결과 번호는 한 번만 반영해요. 서버 검증형은 게임별 결과 검증을 연결해요. 기기에서 신고한 점수는 검증된 기록으로 표시하거나 경쟁 보상의 근거로 쓰지 않아요.
계정·닉네임
NcqAuth를 계정과 닉네임의 원본으로 사용하고 로비·랭킹·친구 화면에 같은 프로필을 표시해요. 게임·테스트/운영 환경을 구분하고, 계정 전환 뒤 이전 계정의 늦은 응답을 적용하지 않아요.
고객지원 ID
NcqAccount가 설정창의 현재 유저 ID 표시·전체 복사를 맡아요. 카카오판은 인증된 플랫폼 원본 ID 연결이 필수예요. 다른 플랫폼은 NcqAuth를 이미 사용하는 게임의 현재 세션 ID를 표시해요.
팝업·공유
NcqPopup을 채택한 게임은 열린 창의 역순으로 뒤로가기를 처리하고, 닫거나 다시 연 화면에 이전 응답을 적용하지 않아요. 공유창도 같은 수명 규격을 사용해요. 기존 게임의 팝업 방식 변경은 사용자가 채택하기로 정했을 때 적용해요.
저장·보상
NcqSave를 쓰는 게임은 재화와 지급 번호를 함께 기록해 중복 지급을 막아요. 결제·초대 보상은 게임의 지급·저장을 완료한 뒤에만 완료를 보고해요. 새 플랫폼의 초대 보상은 NcqInviteRewards로 연결하고, 공유 성공이나 상태 조회만으로 지급하지 않아요.
기기·언어
화면 설정은 NcqDisplay, 진동은 NcqDevice, 소리는 NcqSound로 통일해요. 토스·앱·카카오 SDK의 연결 차이와 켬·끔 설정은 공용 모듈이 맡고, 다국어는 NcqLang의 언어 표와 누락 점검을 사용해요.
안정성 분석
NcqMetrics의 안정성 기록이 포함된 빌드부터 화면을 보던 중 종료된 실행을 다음 실행 때 알려요. 이 값은 비정상 종료 추정치이며 안드로이드 웹뷰 복구 기록도 집계해요. 구글플레이의 공식 크래시·ANR(응답 없음)은 Android vitals에서 확인하고, 같은 종료가 겹칠 수 있어 두 출처를 구분해 봐요.
적용·검증
선택 기능은 해당 게임에서 사용할 때 연결해요. 공용 팝업·공유·프로필 규격을 채택한 게임은 공용 SDK와 완성 화면을 실제 브라우저에서 검사하고 주의사항을 보고해요. 실제 기기의 화면·진동·결제 확인도 함께 구분해 진행해요.

  1. 1. 개발·자료 준비

    게임의 재미와 필요한 지표를 코드에 연결하고 등록 자료를 준비해요.
    우리의 기본 방침·공용 모듈 정보·기존 자료를 재사용하고, 업데이트에서는 바뀐 항목만 보완해요.

    지표 설계·게임 이벤트 연결무엇을 검증할지 제안 · 빠진 기록 연결
    • AI가 기획·코드를 보고 첫 실행·첫 플레이·판 시작과 종료·주요 동선 등 검증에 필요한 기록을 제안해요.
    • 게임 코드에 판·진행 단계·반복 동선을 연결해요. 지표 SDK와 수집 설정은 각 빌드에서 자동으로 포함해요.
    • 수집 한도·중복 제거·묶음 전송은 공용 SDK가 처리하고, 게임은 필요한 시점과 상태만 연결해요.
    • 게임·플랫폼·앱 버전을 구분해 대시보드에서 볼 수 있게 하고, 지표 연결 주의사항은 빌드 전 보고에 남겨요.
    스토어 문구·기본 정보컨셉 재사용 · 언어별 소개 자동 준비
    • 이미 정리한 컨셉과 실제 게임을 바탕으로 앱 이름·짧은 설명·자세한 설명을 작성해요.
    • 실제 게임의 장르와 기능에 맞는 카테고리와 스토어 태그를 골라요.
    • 확정된 회사 정보·기본 설정을 재사용하고, 지원 언어에 맞는 소개를 준비해요.
    스토어 이미지게임 아트 재사용 · 실제 화면 촬영
    • 이미 준비한 자료를 먼저 재사용하고, 빠진 이미지는 AI가 만들어요.
    • 아이콘: 게임 아트로 512 × 512px 이미지를 준비해요.
    • 홍보 그래픽: 핵심 플레이와 분위기가 드러나는 1024 × 500px 이미지를 만들어요.
    • 스크린샷: 게임을 직접 실행해 대표 화면 2~8장을 촬영해요.
    • 완성된 자료를 게임별로 보관해 다음 등록·업데이트에서도 이어서 써요.
    타깃 연령기본 13세 이상 · 확정된 값 재사용

    우리 기본값 · 13세 이상
    13~15세·16~17세·18세 이상을 기본으로 선택해요. 가족 정책을 고려해 기본 출시 대상을 13세 이상으로 두고 있어요.

    우리의 기준AI가 처리하는 방식
    기본 설정13세 이상 3개 구간을 기본으로 준비하고, 실제 기획·게임 화면과 맞는지 확인해요.
    이미 확정한 값프로젝트에 저장된 연령대를 재사용해 콘솔에 같은 값을 입력해요. 정한 내용을 반복해서 묻지 않아요.
    아동 대상 등 예외실제 기획에 맞는 연령과 광고·데이터 처리 등 추가 준비를 별도로 확인해요.
    콘텐츠 등급 설문전체이용가 목표 · 예외 결과만 확인

    우리 기본 방침 · 한국 전체이용가 목표
    기획·연출을 전체이용가 범위에 맞추고, 설문은 실제 게임 내용대로 답해요. 이 게임에 확정해 둔 답은 이후 작업에서 재사용해요.

    확인한 결과자동 진행과 예외 처리
    한국 전체이용가정한 답으로 설문을 채우고 저장해 다음 단계로 진행해요. 같은 답을 다시 확인받지 않아요.
    한국 전체이용가 외 결과12세·15세·청소년이용불가 등이 나오면 저장 전에 결과와 그렇게 나온 답을 보여 주고 확인받아요.
    해외 등급만 높음한국이 전체이용가면 진행하고, 다른 나라의 등급 차이는 결과 보고에 남겨요.
    새 질문·게임 변경기획·코드로 답을 보완하고, 판단하기 어려운 부분이나 실제 앱과 다른 내용만 확인해요.
    AI가 설문 답을 정할 때 보는 내용코드·실제 화면·대사·소리를 함께 확인
    폭력
    전투·무기·상처·유혈 묘사의 대상, 강도와 빈도를 확인해요.
    공포
    위협적인 장면·캐릭터·음악, 놀라게 하는 연출을 확인해요.
    성적인 콘텐츠
    노출·성적 표현·암시가 그림이나 대사에 있는지 확인해요.
    욕설·언어
    화면 글·대사·음성에 포함된 욕설과 표현 수위를 확인해요.
    약물·술·담배
    등장 여부와 사용·미화하는 표현이 있는지 확인해요.
    도박·현금성 보상
    베팅·모의 도박, 현금·기프트 카드·가상자산 등의 보상과 환전 기능을 확인해요.
    사용자 간 소통·공유
    다른 이용자에게 글·채팅·이미지 등을 보낼 수 있는지 확인해요.
    위치 공유
    사용자의 실제 위치를 다른 이용자에게 보여 주는지 확인해요.
    디지털 상품 구매
    유료 재화·아이템·구독과 유료 무작위 상품의 판매 여부를 확인해요.
    외부·온라인 콘텐츠
    앱 안의 브라우저·검색, 다운로드·온라인 추가 콘텐츠의 범위를 확인해요.
    광고·결제 신고빌드 선택값에 맞춰 신고·상품 정보 연결
    • 광고: 이번 빌드에서 켠 광고 지면과 SDK를 보고 광고 포함·광고 ID 사용 여부를 정리해요.
    • 결제: 실제 판매할 상품 ID·종류·가격과 게임에서 지급하는 내용을 정리해요.
    • 광고·상품 설정이 스토어 소개, 데이터 보안 신고와 맞는지 확인해요.
    데이터 보안·개인정보처리방침공통 SDK 신고 자동 작성 · 게임별 데이터 반영

  2. 2. 등록용 진단·테스트 빌드

    구글플레이는 첫 등록용 빌드도 먼저 진단한 뒤 시작해요.
    앱스토어·토스는 이 구글 전용 단계를 건너뛰고 각 플랫폼의 앱 등록·연결로 진행해요.

    1. 등록 요청 접수1단계 자료 확인 → 게시 상황 등록 → 관리자 AI 깨우기

    여기서 확인하는 ‘등록 자료’는 1단계 ‘개발·자료 준비’에서 만들어 저장한 아래 자료예요.

    • 스토어 문구: 앱 이름·짧은 소개·자세한 소개
    • 스토어 이미지: 아이콘·홍보 그래픽·게임 스크린샷
    • 앱 콘텐츠 답변: 카테고리·타깃 연령·콘텐츠 등급 설문 답변 등
    • 데이터 보안 신고: 게임이 별도로 수집·전송하는 데이터가 있을 때 정리한 신고 내용

    서버가 이 자료와 빌드할 게임 코드가 준비됐는지 확인해요. 빠진 항목이 있으면 1단계에서 보완하도록 안내하고, 갖춰졌으면 마켓 등록 요청을 접수해요.

    • 게시 상황과 요청자의 피드백에 진행 상태를 남기고 관리자 측 AI를 깨워요.
    • 빌드가 실패해도 요청 기록을 유지해 관리자 측 AI가 이어서 처리해요.
    2. 등록용 사전 진단게임 설정·고유 앱 ID·권한 설정·1단계 자료 확인

    빌드 전에 코드·설정 파일·저장한 등록 자료를 읽고 아래 항목을 확인해요. 각 항목을 펼치면 무엇을 보고 어떻게 처리하는지 알 수 있어요.

    필수 설정·게임 프로젝트무엇을 어떤 버전으로 빌드할지 확인
    • 확인 대상: 프로젝트 정보, 요청한 앱 버전·버전 코드, 테스트용 빌드 구분, 선택한 광고·상품 설정이에요.
    • 진단: 프로젝트 설정을 읽을 수 있는지, 게임 시작 파일이나 빌드 명령이 있는지, 버전 형식·중복·다른 코드에 사용한 버전과의 충돌이 없는지 확인해요.
    • 처리 예: 게임 코드가 없거나 버전이 충돌하면 중단해요. 공통 빌드 스크립트가 없으면 서버가 넣는 것으로 안내해요.
    앱 식별자 · 패키지명다른 앱의 설정으로 바뀌지 않았는지 확인
    • 뜻: 패키지명은 앱을 구분하는 고유 ID예요. 프로젝트의 bundle_id에 저장된 값이에요.
    • 빌드 전: 저장된 값이 킥오프에서 정한 이 프로젝트의 앱 ID와 일치하는지 확인하고, 다르면 중단해요.
    • 빌드 후: 완성된 AAB에서 실제 앱 ID를 읽어 요청한 값과 다시 대조해요.
    권한·연결 설정마켓 접근과 앱 기능 권한을 구분해 확인
    • 마켓 접근 권한: 서버 계정으로 대상 앱을 읽을 수 있는지 봐요. 첫 등록 전 앱이 아직 없는 것은 안내하고, 이미 연결한 앱에 접근하지 못하면 오류로 처리해요.
    • 앱 기능 권한: 광고 ID·결제·위치·카메라 등 앱이 요청하는 기능이에요. 빌드 전에는 설정 파일과 플러그인 목록을 보고 데이터 보안 신고 누락을 확인해요.
    • 처리 예: 결제 라이브러리 없이 결제 권한만 추가한 설정은 오류예요. 테스트 빌드에서 데이터 신고가 빠진 항목은 주의로 알리고, 배포용 진단에서는 필수 조건으로 확인해요.
    • 완성된 앱에 실제로 어떤 권한이 들어갔는지는 AAB 결과 검사에서 확인해요.
    1단계 등록 자료자료가 있는지 확인한 뒤 형식과 준비 상태 점검
    • 확인 대상: 1단계 ‘개발·자료 준비’의 스토어 문구·이미지·앱 콘텐츠 답변·데이터 보안 신고예요.
    • 진단: 스토어 문구를 읽을 수 있는지, 이미지가 등록 규격에 맞는지, 답변·신고·회사 지원 이메일 등이 준비됐는지 확인해요.
    • 개인정보처리방침 주소가 있으면 열리는지 확인하고, 첫 준비라 아직 없으면 등록 과정에서 생성할 것으로 안내해요.
    선택한 기능·공통 지침광고·결제·지표 연결과 테스트 조건 확인
    • 광고·결제를 켰을 때 필요한 플러그인과 코드 연결이 있는지, 같은 상품을 서로 다른 구매 종류로 사용하지 않는지 확인해요.
    • 광고 ID가 없으면 발급·승인 요청을 시작할 수 있고, 승인 전 테스트 빌드는 테스트 광고를 사용할 수 있어요. 미등록 상품도 먼저 테스트 빌드에 포함한 뒤 등록할 수 있어요.
    • 판 지표·진행 단계·화면 안전 영역·저장·공용 모듈 등 공통 지침의 연결 누락은 주의로 알려요.
    • 테스터 그룹의 설정과 접근 상태도 확인해요.

    진단 결과: 오류는 빌드를 중단하고, 주의는 보완할 내용을 알리되 빌드 자체를 막지 않아요. 안내는 첫 등록·빌드 과정에서 자동으로 준비할 내용이나 현재 상태를 알려 줘요.

    이 단계는 소스와 설정 점검이에요. 완성된 AAB의 실제 값은 아래 ‘결과 검사’에서, 정식 배포 조건은 4단계에서 다시 확인해요.

    3. 등록용 테스트 빌드 실행요청 버전으로 자동 준비 · 같은 빌드는 재사용
    • 구글플레이는 등록 요청을 받으면 요청 버전으로 첫 내부 테스트 빌드를 시작해요.
    • 이미 진행 중이거나 같은 코드·버전으로 만든 빌드가 있으면 재사용해 중복 작업을 줄여요.
    • 선택한 테스트 설정과 필요한 공용 SDK를 연결해 내부 테스트용 AAB를 만들어요.
    • 완료된 결과는 3단계 앱 등록·첫 업로드에 사용해요.
    4. 결과 검사·첫 업로드 파일 준비만들어진 AAB를 검사하고 업로드 키로 서명
    • 완성된 AAB에서 앱 식별자·버전·실제 포함된 권한을 읽어 요청한 설정과 대조해요.
    • 타깃 API·64비트·16KB 페이지·용량 등 실제 결과물이 지원 규격에 맞는지 확인해요.
    • 검사를 통과한 파일을 앱별 업로드 키로 서명하고 첫 업로드에 사용할 수 있게 준비해요.
    • 오류가 있으면 원인과 해결 방법을 정리해 수정·재빌드로 이어가요.

  4. 4. 배포 요청·빌드 전 진단

    정식 배포 조건을 확인하고 필요한 준비로 분기하는 기준점이에요.
    준비됐으면 6단계로, 보완이 필요하면 5단계로 이어가요.

    1. 배포 요청·선택 확정버전과 기능을 한 번 정해 빌드 조건 확정
    • 지난 빌드 이후 바뀐 내용을 모아 버전과 출시 노트 초안을 준비해요.
    • 테스트 기능은 끄고 실제 광고와 판매할 인앱 상품 등 고른 설정을 반영해요.
    • 버전·출시 노트·광고·상품·테스터 등 확정한 선택을 저장해 준비 작업 뒤에도 재사용해요.
    • 아직 실제 배포용 파일은 만들지 않고 진단 결과와 필요한 준비를 먼저 확인해요.
    2. 정식 배포 조건 진단실제 광고·상품·권한·정책 자료를 기준으로 확인
    • 실제 광고 ID, 상품 등록·판매 상태, 권한·데이터 보안·개인정보처리방침·아이콘 등 필수 조건을 확인해요.
    • 판 지표·화면 등 공통 지침은 주의로 알리고, 필수 오류와 구분해요.
    • 2단계의 테스트 빌드 진단과 달리 실제 광고·상품을 사용하는 배포용 조건으로 확인해요.
    3. 진단 결과에 따른 분기준비 완료는 6단계로 · 준비 필요는 5단계로
    • 준비가 끝났으면 5단계를 건너뛰고 6단계 배포용 빌드로 진행해요.
    • 광고 발급·상품 등록·결제 검증 등이 필요하면 5단계의 해당 작업만 진행해요.
    • 코드·자료의 필수 오류는 원인을 고친 뒤 다시 진단해요. 지표 보완이 필요하면 1단계의 연결 내용을 활용해요.
    • 기존 결제 앱의 새 상품 등록처럼 빌드와 병행할 수 있는 작업은 대기 여부를 구분해요.
    4. 보완 후 재확인·빌드 재개같은 요청의 선택을 유지하고 준비 결과 반영
    • 발급·등록·검증 결과가 준비되면 저장한 버전과 선택 설정으로 다시 진단해요.
    • 승인된 결제 준비 흐름은 버전·노트·그룹을 다시 묻지 않고 이어가요.
    • 필수 조건을 통과한 요청만 배포용 빌드로 넘겨요.
  5. 5. 필요한 준비 처리관리자 브라우저

    4단계 진단에서 부족한 것으로 확인한 작업만 진행해요.
    개발 중이나 등록용 빌드에서 이미 준비한 결과는 재사용하고, 추가 발급·등록·검증이 필요한 항목만 처리해요.

    1. 지표 연결 보완진단에서 확인한 누락만 코드에 반영
    • 판·진행 단계 연결이 빠졌으면 AI가 필요한 기록을 제안하고 게임 코드 보완으로 이어가요.
    • 측정 시점과 동선 설계는 1단계 내용을 재사용해요. SDK를 결과물에 넣는 작업은 빌드 단계에서 처리해요.
    • 지표 지침 주의사항은 필수 빌드 오류와 구분해요.
    2. 광고 ID 발급·반영관리자 브라우저고른 광고 지면 확인 → 발급 요청 → 빌드에 연결
    • 게임에서 사용할 광고 지면을 고르면 기존 앱·광고 단위 ID를 먼저 확인하고 재사용해요.
    • 구글플레이 AdMob ID가 없으면 승인 요청을 만들어요. 회사 자동 승인이 켜져 있으면 바로 발급하고, 그 밖에는 관리자 승인 뒤 발급해요.
    • 승인 전 테스트 빌드는 테스트 광고를 사용할 수 있고, 배포용 빌드는 준비된 실제 광고 ID를 반영해요.

    1. 코드·빌드 환경 준비공통 빌드 도구 자동 맞춤 · 준비된 환경 재사용
    • 빌드할 코드 버전을 가져오고, 공통 빌드 스크립트와 도구를 서버가 관리하는 버전으로 맞춰요.

    • 게임의 빌드 설정으로 실행 파일을 만들고, 선택한 플랫폼·앱 버전·기능 설정을 넣어요.

    • 이미 연결해 둔 인증·초대·클라우드 저장 설정과 필요한 앱 플러그인을 포함해요.
    3. 출시 파일 정리·기본 정책 적용개발 자료 제외 · 화면 기본값 · 코드 보호
    • 게임이 사용하지 않는 시험 파일·문서·개발 자료가 출시 결과에 섞이지 않도록 정리해요.
    • 화면 켜두기·글자 배율·확대 방지·연출 정책 등 우리 기본값과 게임별 설정을 반영해요.

  7. 7. 출시 진행관리자 브라우저

    6단계의 배포용 결과물을 올리고 같은 빌드의 검사 결과를 확인해요.
    서명·업로드 → 플랫폼별 테스트 → 심사·공개를 이어가요. 구글·앱스토어는 회사 장비로 검사하고, 토스는 개발자 본인 앱으로 테스트 푸시를 보내 확인해요.

    1. 서명·마켓 업로드확인한 배포용 빌드를 플랫폼에 전달
    플랫폼자동으로 이어가는 작업
    구글플레이앱별 업로드 키로 서명해 비공개 테스트에 올리고, 같은 빌드를 내부 테스트에도 제공해요.
    앱스토어별도 서명 작업으로 아카이브를 검증·서명하고 TestFlight에 올려요.
    토스회사 API로 번들을 올리고, 개발자 대화의 콘솔 MCP로 본인 토스 앱에 테스트 푸시를 보내요. 테스트 링크·QR도 함께 제공해요.
    2. 플랫폼별 테스트 확인구글·앱스토어는 회사 장비 · 토스는 본인 앱 테스트 푸시
    • 구글·앱스토어: 회사 장비에서 업로드한 같은 버전을 확인하고 앱 실행·실행 유지·충돌·화면 기록을 검사해요. 구글은 내부 테스트 트랙, 앱스토어는 TestFlight에 등록된 빌드를 확인해요.
    • 토스: 회사 장비 검사를 사용하지 않아요. 개발자가 본인 토스 앱의 테스트 푸시 알림을 눌러 확인하고 ‘테스트 했어요’를 남겨요. 테스트 링크·QR로도 열 수 있어요.
    • 장비 연결 등 자동 복구 가능한 문제는 먼저 복구하고, 남은 장비 문제는 관리자에게 넘겨요. 실제 앱 실패는 개발 대화에서 고친 뒤 같은 빌드를 다시 검사해요.
    • 결제 지급·광고 클릭·게임 완주 등 기본 실행 검사에 포함되지 않은 항목은 따로 확인해요.
    3. 검토·심사 제출관리자 브라우저플랫폼별 제출 작업을 이어서 처리
    • 구글: 관리자 에이전트가 브라우저로 첫 출시 초안의 국가·지역과 제출 내용을 맞추고 Play Console에서 검토에 보내요.
    • 앱스토어: 배포용 빌드와 아이폰 확인 기록, 심사 자료·연결 상품을 준비해 제출해요.
    • 토스: 앱 정보·이미지는 콘솔 MCP로 먼저 반영해요. 첫 출시는 드라이브 입력표에 게임 등급분류번호가 있으면 관리자 에이전트가 남은 화면 작업과 검토 요청을 진행하고, 없으면 기다려요. 비게임 앱은 게임 등급분류를 요구하지 않아요.
    • 토스 업데이트: 출시를 마친 앱은 본인 앱에서 테스트한 뒤 개발자 대화의 콘솔 MCP로 검토를 요청해요.
    • 자료 작성·화면 입력은 AI가 이어가고, 실제 심사는 각 마켓이 담당해요.
    앱스토어 · 앱 개인정보 입력관리자 브라우저필요한 답을 콘솔에 게시한 뒤 심사 제출 재개
    • 앱 개인정보 답변 게시는 공개 API가 없어, 제출이 이 항목에서 막히면 관리자 에이전트의 콘솔 작업으로 연결해요.
    • 서버가 광고·지표·결제·피드백·클라우드 저장 정보를 바탕으로 준비한 답을 App Store Connect에서 입력·게시해요.
    • 완료하면 기존 심사 제출을 다시 요청해요. 서명·TestFlight·일반 심사 제출·공개는 서버 도구로 이어가요.
    4. 승인 후 공개관리자 브라우저승인 상태와 선택한 공개 범위 반영
    • 구글: 첫 출시는 별도 지시가 없으면 프로덕션 100% 공개까지 준비해요. 국가·지역 설정과 심사·게시 상태 확인은 브라우저로 하고, 프로덕션 승격은 서버 도구로 진행해요.
    • 앱스토어: Apple이 승인한 버전을 공개해요.
    • 토스: 승인·반려 상태는 콘솔 MCP로 확인해요. 승인됐으면 관리자 에이전트가 브라우저에서 ‘출시하기’를 진행해요.
    • 첫 공개는 관리자가 진행하고, 이후 업데이트는 각 플랫폼의 프로젝트 권한에 따라 이어가요.
    5. 출시 기록·다음 업데이트실제 공개 상태를 확인하고 기록 연결
    • 실제 마켓 상태와 출시 버전·사용한 빌드를 확인해 대시보드 기록을 맞춰요.
    • 구글·토스의 첫 출시 완료는 관리자가 표시하고, 앱스토어는 Apple에서 읽은 상태를 반영해요.

  1. 1. 모객 계획목표 수·기간·예산·측정기간 설정

    기본 계획으로 시작할 수 있고, 게임의 검증 목적이나 허용 비용이 다를 때 조정해요. 시작 전에 확인할 가설 1~3개와 출시 버전, 유료 모객 또는 자연 유입을 정하고, 관리자가 계획과 집계 시작을 승인해요.

    목표 수기본 신규 500명 · 판단에 필요한 표본 확보
    • 설정 기준: 재방문율을 판단할 만큼 신규 표본을 모으는 것이 목적이에요. 현재 서버의 판정 추천에는 최소 350명이 필요하고, 처음에는 여유를 두어 500명을 목표로 해요.
    • 설정 방법: 사이클의 목표 신규 수에 기본 500명을 넣어요. 더 많은 표본이 필요한 검증은 예산·기간도 함께 검토해 목표를 늘려요. 현재 입력 범위는 350~5,000명이에요.
    • 집계 대상: 해당 기간·플랫폼·버전을 처음 실행한 설치예요. 자연 유입도 포함될 수 있어요.
    • 유료 모객은 예산·기간이 먼저 끝나면, 자연 유입은 기간이 끝나면 실제 표본 수를 남겨요. 350명 미만이면 성과 판정을 보류해요.
    모객 기간기본 최대 10일 · 학습·속도 조정 시간 고려
    • 설정 기준: 광고가 학습하고 목표 인원을 모을 시간을 확보해요. 구글은 처음 3일 동안 단가를 유지하고, 그 뒤 최소 2일 간격으로 조정하므로 기본 10일로 시작해요.
    • 설정 방법: 사이클의 모객 일수에 기본 10일을 넣어요. 이전 모객 속도를 보고 다음 계획의 목표 수·예산과 함께 기간을 조정해요. 현재 입력 범위는 3~30일이에요.
    • 진행 기준: 목표 수 ÷ 모객 일수로 하루 기대 신규 수를 봐요. 기본 500명·10일이면 하루 평균 50명이 계획 속도예요.
    • 유료 모객은 목표 신규 수·예산·종료일 중 먼저 닿으면 마쳐요. 자연 유입은 목표 신규 수·종료일로 종료하고, 잠시 멈춘 시간은 기간에서 빼요.
    예산기본 구글 10만 원 · 토스 2만 원
    • 설정 기준: 목표 표본을 모을 예상 단가와 한 사이클에 허용할 비용을 함께 검토해요. 첫 검증은 현재 회사 기본 예산에서 시작하고, 이전 집행 기록이 있으면 목표 수 × 예상 모객 단가로 필요한 금액을 다시 계산해요.
    • 설정 방법: 사이클 예산에 구글플레이 10만 원, 토스 2만 원을 기본으로 넣고 관리자가 승인해요. 현재 입력 범위는 1만~1,000만 원이며, 금액을 크게 바꿀 때는 표본·기간도 함께 검토해요.
    • 구글: 총예산과 모객 일수로 일 예산을 계산해요. 기본은 하루 1만 원이에요. 목표 설치 단가는 예산·목표 표본으로 계산해 기본 120원에서 시작하고 최대 280원까지 조정해요.
    • 토스: 미션 보상 금액과 프로모션 한도를 함께 확인하고, 실제 포인트 지급액으로 비용을 집계해요.
    • 예산 도달 확인과 비용 반영이 늦으면 실제 지출이 설정 예산을 넘을 수 있어요. 토스 프로모션 시작·중지는 관리자 콘솔에서 맞춰요. 자연 유입을 선택한 사이클은 광고·프로모션 비용 없이 집계해요.
    측정기간모객 종료 후 7일 · 마지막 신규의 D7 확인
    • 설정 기준: 마지막에 들어온 유저도 7일 뒤 다시 오는지 확인할 수 있어야 해요. 모객 종료 뒤 7일을 더 관찰하도록 잡아요.
    • 현재 적용: 측정기간은 검증 서버의 공통 7일 고정값이에요. 사이클 화면에서 목표 수·모객 기간·예산처럼 바꾸는 입력 항목은 없어요.
    • 일정 예: 10일 모객을 모두 진행하면 그 뒤 7일을 더 측정해요. 목표·예산에 먼저 닿아 모객을 끝내면 그 종료 시점부터 7일을 관찰해요.
    • D1·D3는 중간 흐름을 확인하고, 마지막 신규의 D7까지 관찰한 뒤 최종 판정을 진행해요.

    • 선택한 플랫폼의 출시 완료 기록, 실제 지표 유입, 판 시작 지표와 진행 단계 기록을 확인해요.

    • 최근 하루 평균 신규 × 모객 일수로 예상 표본을 계산해요. 최소 350명 이상이 예상되면 광고·프로모션 없이 자연 유입으로 검증할 수 있어요.

    • 목표 신규 수나 종료일에 닿으면 추가 관찰로 넘어가요. 광고·프로모션으로 모은 유저와 성격이 다를 수 있어 결과를 구분해 비교해요.
    구글플레이 · Google Ads 앱 캠페인나라·문구·단가를 준비하고 일시중지로 생성
    • 회사 광고 계정과 앱 연결을 재사용해요. 첫 연결의 계정 로그인·결제 수단·Play Console 연결은 관리자가 준비해요.

    • 게임 이름을 바탕으로 기본 광고 제목·설명을 준비하고, 예산·목표 신규 수로 일 예산과 목표 설치 단가를 계산해요.
    • 연결·나라 등 필요한 값이 갖춰지면 서버가 캠페인을 미리 만들어요. 시작 승인 전에는 일시중지 상태로 둬요.
    목표 설치 단가 조정처음 3일 유지 · 모객이 느리면 조금씩 조정
    • 시작 단가는 예산 ÷ 목표 신규 수의 60%를 기준으로 계산해요. 현재 기본값에서는 약 120원이에요.
    • 캠페인을 켠 뒤 3일 동안은 단가를 유지해요.
    • 이후 신규 수가 계획 속도의 80%보다 적으면 최소 2일 간격으로 목표 단가를 25%씩 올려요.
    • 올릴 수 있는 끝은 예산과 최소 판단 표본을 기준으로 계산하며, 관리자가 시작값·최댓값을 조정할 수 있어요.
    토스 · 미션 프로모션기존 미션 코드 연결 · 실제 지급액으로 비용 집계
    • 킥오프에 저장한 토스 프로모션 설정에서 콘솔 코드가 있고 유효한 미션을 읽어 모객 준비를 채워요.
    • 미션·보상 금액·기간·코드 등록은 관리자와 토스 콘솔에서 준비해요. 관리자가 이미 고른 설정은 유지해요.
    • 게임에서 토스 포인트를 실제 지급한 기록으로 모객 비용을 합산해요. 테스트 지급과 중복 기록은 제외해요.

    • 관리자가 준비 체크리스트와 모객 계획을 확인하고 ‘사이클 집계 시작’을 승인해요. 유료 모객은 예산을, 자연 유입은 광고비 없이 집계할 경로와 예상 표본을 확인해요.
    • 이 시점을 시작 기록으로 남기고 신규 수와 비용을 집계해요. 유료 모객의 구글 캠페인은 서버가 켜고, 자연 유입 사이클에서는 켜지 않아요.
    • 토스 프로모션의 실제 시작·중지는 관리자가 콘솔에서 진행해요. 검증 서버의 집계 상태와 함께 맞춰요.

    • 유료 모객은 목표 신규 수·예산 한도·종료일 중 먼저 닿은 조건으로, 자연 유입은 목표 신규 수·종료일로 ‘측정 중’에 넘어가요. 켜 둔 구글 캠페인은 서버가 중지해요.
    • 신규는 해당 기간·플랫폼·버전을 처음 실행한 설치를 기준으로 세며, 자연 유입도 포함될 수 있어요.

    유료 모객은 예산에 닿으면 중지해요. 주기 확인과 비용 반영이 늦으면 실제 지출이 설정 예산을 넘을 수 있어요. 토스 프로모션 중지는 관리자 콘솔 확인이 필요하며, 자연 유입에는 예산 종료 조건을 적용하지 않아요.

    • 심한 오류가 있으면 이유를 남기고 모객을 잠시 멈춰요. 멈춘 시간은 모객 기간에서 빼요.
    • 버그 수정 버전은 ‘핫픽스로 이어가기’로 연결하고 두 버전을 함께 측정했다는 기록을 남겨요.
    • 난이도·보상·화면 흐름처럼 게임 내용을 바꾸면 판정 후 다음 사이클로 가거나, 현재 사이클을 취소하고 새로 시작해요.
  5. 5. D7 측정·결과 정리마지막 신규의 7일 뒤 재방문까지 관찰
    • 모객이 끝나도 7일 더 관찰해 마지막에 들어온 사람의 D7까지 확인해요.
    • D1·D3·D7 재방문율, 첫날 플레이 시간, 판 진행·이탈 지점, 모객 비용을 정리해요.
    • 지난 사이클과 비교하고 서버의 판정 추천·이유를 보여 줘요.
    • 현재 추천 기준에서 신규 350명 미만 등 표본이 부족하면 판단하기 이르다고 표시해요.

    모객 중의 이상 상황은 아래 기준으로 대처하고, 모객 종료 후에는 마지막 신규의 D7까지 관찰해요. 자연 유입과 유료 모객의 결과는 유입 성격을 구분해 비교해요. 숫자와 추천 이유를 바탕으로 개발자가 AI와 결과를 해석하고, 최종 선택과 이유를 검증 화면에 남겨요.

    확장·개선·중단 기준과 다음 행동어떤 결과일 때 선택하고, 무엇을 이어가는가

    D1·D7은 처음 쓴 1일·7일 뒤 다시 온 비율이에요. 신규 350명 이상과 D1 자료를 확보하고 마지막 신규의 D7까지 관찰한 뒤, 세 항목의 기준과 의미를 확인해요.

    현재 D1을 첫 개선 사이클과 비교하고, 모객·업데이트에 대한 추가 투입을 멈추는 쪽을 검토해요. 쓴 비용과 중단 이유를 기록해요.

    • 판 중단률: 해당 판을 시작한 사람 중 끝내지 않은 비율이에요. 시작한 사람이 30명 이상인 판만 개선 추천에 사용해요.

    • 첫 사이클의 예: D1 42%·D7 16%는 확장 검토, D1 42%·D7 10%는 개선 검토예요. D1 22%여도 판 중단률이 35%라면 개선할 지점으로 봐요. 반복 개선 한도에 닿으면 중단 검토를 먼저 해요.
    • 확장 조건을 먼저 확인해요. 확장에 해당하지 않고 반복 개선 한도에 닿았다면 중단을 우선 검토해요. 서버의 추천과 이유를 보고 사람이 최종 선택을 기록해요.

    예산·기간유료: 구글 10만 원 / 토스 2만 원
    기본 최대 10일    		유료 모객은 목표 신규·예산·종료일로, 자연 유입은 광고비 없이 목표 신규·종료일로 마쳐요. 구글 광고는 자동 중지하고, 토스 프로모션은 관리자 콘솔에서 중지해요.

    표는 좌우로 움직여 볼 수 있어요.

    속도 기준은 목표 신규 × 지난 일수 ÷ 모객 일수로 계산해요. 기본값으로 캠페인 시작 후 4일이 지났을 때 기대치는 200명이고, 160명 미만이면 단가 조정 대상이에요. 목표 단가는 광고에 설정하는 입찰 목표이며, 신규 수에는 자연 유입도 포함될 수 있어요.

    120원·280원은 현재 기본 예산과 표본에서 계산한 값이에요. 예산·목표를 바꾸면 다시 계산하고, 관리자가 시작값·최댓값을 조정할 수 있어요. 예산 도달 확인과 비용 반영에는 지연이 있을 수 있어요.

    • 추가할 기준 초안: 같은 나라·플랫폼·유입 집단에서 유저 1명당 누적 순수익과 실제 유료 획득 비용을 비교하고, 언제까지 비용을 회수할지 정해요.
